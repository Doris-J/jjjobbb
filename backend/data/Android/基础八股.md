## 一、Activity

### Q1：Activity 完整生命周期？

```
onCreate → onStart → onResume → [运行中]
                                     ↓
                               onPause
                                     ↓
                  ┌── onStop → onDestroy
                  └── onRestart → onStart
```

**场景分析：**

| 场景 | 生命周期 |
|------|---------|
| 正常启动 | onCreate→onStart→onResume |
| 按 Home 键 | onPause→onStop |
| 返回前台 | onRestart→onStart→onResume |
| 按 Back 键 | onPause→onStop→onDestroy |
| 横竖屏（未配置） | 销毁重建全走一遍 |
| 横竖屏（configChanges） | onConfigurationChanged |
| 弹出 Dialog | 无变化（同进程） |
| 启动透明 Activity | onPause（不调用 onStop） |

---

### Q2：Activity 四种启动模式？

| 模式 | 特点 | 使用场景 |
|------|------|---------|
| standard | 每次新建实例 | 默认，普通页面 |
| singleTop | 栈顶复用（onNewIntent） | 通知跳转、推送页面 |
| singleTask | 栈内复用，清除其上 Activity | 主页、首页 |
| singleInstance | 独享任务栈 | 拨号、闹钟 |

**常用 Intent Flag：**
- `FLAG_ACTIVITY_NEW_TASK`：新任务栈
- `FLAG_ACTIVITY_CLEAR_TOP`：清除栈顶到目标之间的 Activity
- `FLAG_ACTIVITY_SINGLE_TOP`：同 singleTop

---

### Q3：onSaveInstanceState 调用时机？

- 系统主动回收时触发（非用户主动按 Back）
- API28 后在 onStop 之后调用

```kotlin
override fun onSaveInstanceState(outState: Bundle) {
    super.onSaveInstanceState(outState)
    outState.putString("key", value)
}

override fun onCreate(savedInstanceState: Bundle?) {
    super.onCreate(savedInstanceState)
    val value = savedInstanceState?.getString("key")
}
```

```
onAttach → onCreate → onCreateView → onViewCreated
→ onStart → onResume → [运行]
```

**add vs replace：**

## 五、ContentProvider

### Q7：ContentProvider 实现原理？

- 基于 Binder 实现跨进程数据共享
- 通过 URI 标识数据（`content://authority/path/id`）
- 启动时机：Application onCreate **之前**初始化（常用于 SDK 无侵入初始化）

```kotlin
class MyProvider : ContentProvider() {
    override fun onCreate(): Boolean {
        // 初始化数据库等
        return true
    }
    override fun query(uri: Uri, projection: Array<String>?,
        selection: String?, selectionArgs: Array<String>?,
        sortOrder: String?): Cursor? { return null }
    override fun insert(uri: Uri, values: ContentValues?): Uri? { return null }
    override fun delete(uri: Uri, selection: String?,
        selectionArgs: Array<String>?): Int { return 0 }
    override fun update(uri: Uri, values: ContentValues?,
        selection: String?, selectionArgs: Array<String>?): Int { return 0 }
    override fun getType(uri: Uri): String? { return null }
}
```

## 六、Handler 消息机制

### Q8：Handler 完整工作流程？

```
Handler.sendMessage(msg)
    → MessageQueue.enqueueMessage()  // 按 when 时间排序插入链表

Looper.loop()
    → MessageQueue.next()            // 取消息（无消息时阻塞）
    → Handler.dispatchMessage(msg)
        → msg.callback != null       → handleCallback(msg)
        → handler.mCallback != null  → mCallback.handleMessage(msg)
        → 默认                       → handleMessage(msg)
```

**核心组件：**
- **Message：** 消息载体，享元模式（obtain() 复用，避免频繁创建）
- **MessageQueue：** 单链表，按 when 时间排序
- **Looper：** 每线程唯一（ThreadLocal 存储），循环取消息
- **Handler：** 发送和处理消息的入口

---

### Q9：主线程的 Looper 为何不会导致 ANR？

`MessageQueue.next()` 调用 `nativePollOnce()`，底层使用 **Linux epoll 机制**：

- 无消息时：epoll_wait 阻塞，**释放 CPU，不消耗资源**
- 有消息时：通过向 pipe 写入字节来唤醒
- 有延时消息：epoll_wait 设置超时时间到期自动唤醒

> ANR 不是 Looper 阻塞导致，而是某条消息的**处理时间过长**导致

---

### Q10：同步屏障（消息屏障）原理？

```java
// 插入屏障（target 为 null 的特殊 Message）
int token = handler.getLooper().getQueue().postSyncBarrier();

// 发送异步消息（可以越过屏障）
Message msg = Message.obtain();
msg.setAsynchronous(true);
handler.sendMessage(msg);

// 移除屏障
handler.getLooper().getQueue().removeSyncBarrier(token);
```

**作用：** 屏障插入后，所有普通同步消息被暂停处理，只处理异步消息

**应用：** Choreographer 使用异步消息保证 VSync 信号优先处理，提升帧率

---

### Q11：IdleHandler？

```java
Looper.myQueue().addIdleHandler(new MessageQueue.IdleHandler() {
    @Override
    public boolean queueIdle() {
        doLazyInit(); // MessageQueue 空闲时执行
        return false; // false：执行一次后移除；true：每次空闲都执行
    }
});
```

**应用：** 启动优化中延迟初始化非关键 SDK

### Q12：Handler 内存泄漏？

**原因链：** 非静态内部类 Handler 持有外部 Activity 引用
→ 未处理的 Message 持有 Handler → Activity 无法被 GC 回收

```kotlin
// 解决：静态内部类 + 弱引用
class MyHandler(activity: MainActivity) : Handler(Looper.getMainLooper()) {
    private val weakRef = WeakReference(activity)
    override fun handleMessage(msg: Message) {
        weakRef.get()?.run { /* 处理消息 */ }
    }
}

// onDestroy 中移除所有消息和回调
override fun onDestroy() {
    super.onDestroy()
    handler.removeCallbacksAndMessages(null)
}
```

## 七、Binder

### Q13：Binder 通信原理（一次拷贝）？

```
传统 IPC：
  用户空间A → 内核缓冲区（拷贝1）→ 用户空间B（拷贝2）   共 2 次

Binder IPC：
  用户空间A → 内核空间（拷贝1）
  内核空间  ← mmap 映射 → 接收进程用户空间（无需拷贝）  共 1 次
```

**关键技术：mmap（内存映射）**
- Binder 驱动在内核申请内存
- 该内存同时映射到接收进程的用户空间
- 发送方拷贝数据到内核，接收方直接可见

**与其他 IPC 对比：**

| IPC 方式 | 拷贝次数 | 特点 |
|---------|---------|------|
| Binder | 1 | 安全（UID/PID 鉴权）、高效 |
| 共享内存 | 0 | 最快，但需同步机制 |
| Socket | 2 | 通用，适合跨网络 |
| 管道 | 2 | 单向，流式 |

---

### Q14：Binder 通信角色与 AIDL 流程？

| 角色 | 说明 |
|------|------|
| Client | 服务调用方 |
| Server | 服务提供方 |
| ServiceManager | Binder 的"DNS"，管理服务注册与查询 |
| Binder 驱动 | 内核层，实际通信媒介 |

**AIDL 生成代码分析：**

```
Client → Proxy.transact(code, data, reply)
       → Binder 驱动（跨进程传递）
       → Stub.onTransact(code, data, reply)
       → Server 实现方法
```

---

### Q15：Binder 线程池？

- Server 进程中 Binder 驱动维护线程池（默认最大 15+1 线程）
- 主线程（Main Binder Thread）+ 普通 Binder Thread
- 客户端默认同步阻塞调用（oneway 关键字修饰则异步非阻塞）

## 八、进程

### Q16：进程优先级与回收机制（OOM Adj）？

| 优先级 | 说明 | 回收可能性 |
|--------|------|----------|
| 前台进程（Foreground） | 正在交互的 Activity | 极低 |
| 可见进程（Visible） | 可见但非焦点 | 低 |
| 服务进程（Service） | 运行 Service | 中 |
| 后台进程（Background） | 不可见 Activity | 高 |
| 空进程（Empty） | 无活跃组件 | 最高 |

---

### Q17：进程保活方案？

- 前台 Service（显示通知，提升优先级至可见进程级别）
- JobScheduler / WorkManager（系统调度，省电）
- 双进程守护（相互拉起，Android 高版本限制增多）
- 系统级推送（厂商推送通道：FCM/小米/华为）

---

### Q18：多进程通信方案对比？

| 方案 | 适用场景 |
|------|---------|
| AIDL | 复杂接口调用、高频通信 |
| Messenger | 简单消息传递（基于 AIDL） |
| ContentProvider | 数据共享 |
| Socket | 本地或网络通信 |
| 共享内存 | 大量数据传输 |

## 九、View 绘制流程

### Q19：三大流程详解？

```
ViewRootImpl.performTraversals()
    ↓
performMeasure() → View.measure() → onMeasure()
    ↓
performLayout()  → View.layout()  → onLayout()
    ↓
performDraw()    → View.draw()    → onDraw()
```

**MeasureSpec 三种模式：**

| 模式 | 含义 | 对应布局属性 |
|------|------|------------|
| EXACTLY | 精确值 | match_parent / 固定 dp |
| AT_MOST | 不超过该值 | wrap_content |
| UNSPECIFIED | 无限制 | ScrollView 子 View |

**Draw 顺序：**
1. 绘制背景 `drawBackground()`
2. 绘制自身 `onDraw()`
3. 绘制子 View `dispatchDraw()`
4. 绘制前景/滚动条

---

### Q20：invalidate vs requestLayout？

| 方法 | 触发流程 | 使用场景 |
|------|---------|---------|
| invalidate() | 只触发 onDraw() | 内容变化（颜色、文字） |
| requestLayout() | 触发 measure+layout+draw | 尺寸/位置变化 |
| postInvalidate() | 子线程调用 invalidate | 子线程更新 UI |

---

### Q21：自定义 View 注意事项？

```kotlin
class MyView @JvmOverloads constructor(
    context: Context,
    attrs: AttributeSet? = null,
    defStyleAttr: Int = 0
) : View(context, attrs, defStyleAttr) {

    // 1. 构造中初始化 Paint，避免 onDraw 中创建对象（触发 GC）
    private val paint = Paint(Paint.ANTI_ALIAS_FLAG).apply {
        color = Color.RED
        strokeWidth = 4f
    }

    // 2. 重写 onMeasure 支持 wrap_content
    override fun onMeasure(widthMeasureSpec: Int, heightMeasureSpec: Int) {
        val defaultSize = 200
        val width = when (MeasureSpec.getMode(widthMeasureSpec)) {
            MeasureSpec.EXACTLY  -> MeasureSpec.getSize(widthMeasureSpec)
            MeasureSpec.AT_MOST  -> minOf(defaultSize, MeasureSpec.getSize(widthMeasureSpec))
            else -> defaultSize
        }
        setMeasuredDimension(width, width)
    }

    // 3. 处理 padding
    override fun onDraw(canvas: Canvas) {
        val left   = paddingLeft.toFloat()
        val top    = paddingTop.toFloat()
        val right  = (width - paddingRight).toFloat()
        val bottom = (height - paddingBottom).toFloat()
        canvas.drawRect(left, top, right, bottom, paint)
    }
}
```

## 十、VSync 与渲染机制

### Q22：VSync 机制与 Choreographer？

```
硬件每 16.6ms 发出 VSync 信号（60fps）
    ↓
Choreographer 接收 VSync 信号
    ↓
按顺序执行：Input → Animation → Traversal（measure/layout/draw）
    ↓
生成 DisplayList → 提交给 RenderThread
    ↓
SurfaceFlinger 合成所有图层 → 显示到屏幕
```

**双缓冲：** Front Buffer（显示）+ Back Buffer（CPU/GPU绘制），VSync 时交换

**三缓冲：** 再增加一个缓冲区，CPU/GPU 可提前准备下一帧，减少 Jank（掉帧）

---

### Q23：Surface / SurfaceView / TextureView 区别？

| 特性 | SurfaceView | TextureView |
|------|------------|-------------|
| 独立 Surface | ✅ 有独立绘制线程 | ❌ 与 View 树共用 |
| 动画/旋转/缩放 | ❌ 不支持 | ✅ 支持 |
| 性能 | 更高 | 略低（需额外合成） |
| 透明度 | ❌ | ✅ |
| 使用场景 | 视频播放、相机预览 | 需要变换/动画的视频 |

---

### Q24：硬件加速原理？

- 开启后绘制操作转交 GPU 处理
- 使用 **DisplayList** 记录绘制指令（可复用，只重绘脏区域）
- 不支持硬件加速的操作：部分 Canvas API、某些 Xfermode
- 层级渲染：`view.setLayerType(LAYER_TYPE_HARDWARE, null)`

## 十一、事件分发

### Q25：事件分发完整流程？

```
Activity.dispatchTouchEvent()
    → PhoneWindow.superDispatchTouchEvent()
        → DecorView.dispatchTouchEvent()
            → ViewGroup.dispatchTouchEvent()
                → onInterceptTouchEvent()
                    ↓ true（拦截）
                    → ViewGroup.onTouchEvent()
                    ↓ false（不拦截）
                    → 子 View.dispatchTouchEvent()
                        → View.onTouchEvent()
                            ↓ false（不消费）
                            → 回传父 View.onTouchEvent()
```

**关键规则：**
- 一旦子 View 消费了 DOWN，后续 MOVE/UP 直接传给该 View
- `requestDisallowInterceptTouchEvent(true)` 禁止父 View 拦截
- 返回 true 代表消费事件，不再继续传递

### Q26：NestedScrolling 机制？

解决父子 View 同向滑动冲突（如 RecyclerView 嵌套 CoordinatorLayout）：


## 十二、RecyclerView

### Q27：四级缓存？

```
一级缓存：mAttachedScrap / mChangedScrap
    → 屏幕内 ViewHolder，不需要重新绑定（不调用 onBindViewHolder）

二级缓存：mCachedViews（默认 2 个）
    → 刚离屏的 ViewHolder，不需要重新绑定（保留原有数据）

三级缓存：ViewCacheExtension（自定义）
    → 开发者自定义缓存策略（较少使用）

四级缓存：RecycledViewPool
    → 按 ViewType 分组存储，需要重新绑定（调用 onBindViewHolder）
    → 可跨多个 RecyclerView 共享
```

**性能优化：**

```kotlin
recyclerView.apply {
    setHasFixedSize(true)       // 固定尺寸，不触发 requestLayout
    setItemViewCacheSize(4)     // 调大二级缓存
    recycledViewPool.setMaxRecycledViews(TYPE_ITEM, 20) // 调大 Pool
}

// DiffUtil 局部刷新（避免全量 notifyDataSetChanged）
val diffResult = DiffUtil.calculateDiff(MyDiffCallback(oldList, newList))
diffResult.dispatchUpdatesTo(adapter)
```
