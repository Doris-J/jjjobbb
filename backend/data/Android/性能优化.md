## 一、启动优化

### Q1：启动类型与指标？

| 类型 | 定义 | 优化目标 |
|------|------|---------|
| 冷启动 | 进程不存在，完全重建 | < 2s |
| 温启动 | 进程存在，Activity 重建 | < 1s |
| 热启动 | Activity 在后台，直接显示 | < 500ms |

**冷启动完整流程：**

```
点击图标
    → Launcher 通知 AMS
    → AMS 通知 Zygote fork 新进程
    → 进程创建，加载 ActivityThread
    → Application.attachBaseContext()（MultiDex 在此处理）
    → Application.onCreate()（SDK 初始化）
    → Activity.onCreate / onStart / onResume
    → View 测量、布局、绘制
    → 第一帧绘制完成（TTID：Time To Initial Display）
    → 列表/内容完整加载（TTFD：Time To Full Display）
```

### Q2：启动优化策略？

**策略 1：异步初始化（有向无环图任务调度）**

```kotlin
// 定义任务
abstract class Task {
    abstract fun run()
    open fun dependsOn(): List<Class<out Task>> = emptyList()
    open fun runOnMainThread(): Boolean = false
    open fun needAwait(): Boolean = false // 是否需要主线程等待完成
}

// 实现具体任务
class LogTask : Task() {
    override fun run() { Logger.init() }
    override fun runOnMainThread() = false
}

class InitTask : Task() {
    override fun run() { SDK.init() }
    override fun dependsOn() = listOf(LogTask::class.java) // 依赖 LogTask
    override fun runOnMainThread() = false
}

class MainTask : Task() {
    override fun run() { MainSDK.init() }
    override fun dependsOn() = listOf(InitTask::class.java)
    override fun runOnMainThread() = true  // 必须主线程
    override fun needAwait() = true        // 主线程等待此任务
}

// 调度器（拓扑排序 + 并行执行）
TaskDispatcher.init()
    .addTask(LogTask())
    .addTask(InitTask())
    .addTask(MainTask())
    .start()
    .await() // 等待 needAwait=true 的任务完成后继续
```

## 二、内存优化

### Q4：Bitmap 优化？

```kotlin
// 1. 按需采样加载（inSampleSize 降采样）
fun decodeSampledBitmap(
    res: Resources, resId: Int,
    reqWidth: Int, reqHeight: Int
): Bitmap {
    val options = BitmapFactory.Options().apply {
        inJustDecodeBounds = true          // 只读宽高，不分配内存
        BitmapFactory.decodeResource(res, resId, this)
        inSampleSize = calculateInSampleSize(this, reqWidth, reqHeight)
        inJustDecodeBounds = false
        inPreferredConfig = Bitmap.Config.RGB_565 // 无透明通道时使用，内存减半
    }
    return BitmapFactory.decodeResource(res, resId, options)
}

fun calculateInSampleSize(
    options: BitmapFactory.Options,
    reqWidth: Int, reqHeight: Int
): Int {
    val (height, width) = options.outHeight to options.outWidth
    var inSampleSize = 1
    if (height > reqHeight || width > reqWidth) {
        val halfHeight = height / 2
        val halfWidth  = width / 2
        while (halfHeight / inSampleSize >= reqHeight &&
               halfWidth  / inSampleSize >= reqWidth) {
            inSampleSize *= 2
        }
    }
    return inSampleSize
}

// 2. 格式选择对比
// ARGB_8888：4 字节/像素（默认，高质量，有透明通道）
// RGB_565：  2 字节/像素（无透明通道，内存减半，轻微色彩损失）
// ARGB_4444：已废弃
// HARDWARE： API 31+，直接存储在 GPU 内存，适合只展示不修改的图片

// 3. Bitmap 复用（inBitmap，API 19+）
val options = BitmapFactory.Options().apply {
    inMutable = true
    inBitmap  = reusableBitmap // 复用已有 Bitmap 的内存，避免重新分配
}

// 4. 大图分块加载（BitmapRegionDecoder）
val decoder = BitmapRegionDecoder.newInstance(inputStream, false)
val region = Rect(0, 0, 1000, 1000) // 只解码指定区域
val bitmap = decoder.decodeRegion(region, BitmapFactory.Options())

// 5. 使用完及时回收
if (!bitmap.isRecycled) {
    bitmap.recycle()
}
```

### Q5：内存泄漏常见场景？

| 场景 | 根因 | 解决方案 |
|------|------|---------|
| 静态变量持有 Context | 静态生命周期 > Activity | 改用 ApplicationContext 或弱引用 |
| Handler 非静态内部类 | 持有外部 Activity 引用 | 静态内部类 + 弱引用，onDestroy 清除消息 |
| 单例持有 Activity | 单例生命周期 > Activity | 传 ApplicationContext |
| RxJava 未取消订阅 | Observable 持有 Observer | CompositeDisposable + onDestroy clear |
| 协程未取消 | 协程持有外部引用 | 使用 lifecycleScope / viewModelScope |
| 资源未关闭 | Cursor / Stream / Bitmap 占用 | try-finally 或 use{} 块 |
| 匿名内部类 / Lambda | 隐式持有外部类引用 | 改为静态或提取为顶层函数 |
| 集合缓存未清理 | 对象存入集合后不删除 | 使用 WeakHashMap 或手动清理 |

**LeakCanary 原理：**

```
1. 监听 Activity / Fragment onDestroy 回调
2. 对目标对象创建弱引用 + 关联 ReferenceQueue
3. 延迟 5 秒后手动触发 GC
4. 检查弱引用是否入队 ReferenceQueue
   → 入队：对象已被回收，正常
   → 未入队：对象可能泄漏
5. Dump Heap（.hprof 文件）
6. 分析堆文件，找到 GC Root 到泄漏对象的最短引用链
7. 在通知栏展示泄漏路径
```

### Q6：内存抖动（Memory Churn）？

**原因：** 短时间内大量对象创建和销毁，频繁触发 GC，导致帧率不稳定

**常见场景：**

```kotlin
// ❌ onDraw 中频繁创建对象
override fun onDraw(canvas: Canvas) {
    val paint = Paint()           // 每帧都创建
    val rect  = RectF()          // 每帧都创建
    canvas.drawRect(rect, paint)
}

// ✅ 在构造函数或 init 块中初始化
private val paint = Paint(Paint.ANTI_ALIAS_FLAG)
private val rect  = RectF()

// ❌ 循环中字符串拼接（产生大量临时 String 对象）
var result = ""
for (item in list) {
    result += item  // 每次 + 都创建新 String
}

// ✅ 使用 StringBuilder
val sb = StringBuilder()
for (item in list) sb.append(item)
val result = sb.toString()

// ❌ 自动装箱（基本类型 → 包装类）
val map = HashMap<Int, Int>()
map[1] = 1  // int → Integer，创建包装对象

// ✅ 使用 SparseArray / SparseLongArray
val sparseArray = SparseArray<Int>()
sparseArray.put(1, 1)
```

### Q8：卡顿检测方案？

**方案 1：BlockCanary（基于 Looper Printer）**

```kotlin
// 原理：Looper 每次分发消息前后都会打印日志
// 通过替换 Printer 计算消息处理耗时

class BlockMonitor : Printer {
    private var startTime = 0L

    override fun println(x: String) {
        if (x.startsWith(">>>>> Dispatching")) {
            startTime = SystemClock.elapsedRealtime()
        } else if (x.startsWith("<<<<< Finished")) {
            val cost = SystemClock.elapsedRealtime() - startTime
            if (cost > BLOCK_THRESHOLD) {
                // 主线程卡顿，上报堆栈
                reportBlockStack(cost)
            }
        }
    }
}

// 安装监控
Looper.getMainLooper().setMessageLogging(BlockMonitor())
```

**方案 2：Choreographer 帧率监控**

```kotlin
class FPSMonitor : Choreographer.FrameCallback {
    private var lastFrameTime = 0L
    private var frameCount    = 0

    override fun doFrame(frameTimeNanos: Long) {
        if (lastFrameTime != 0L) {
            val frameCost = (frameTimeNanos - lastFrameTime) / 1_000_000 // 转ms
            if (frameCost > 32) { // 超过 2 帧时间（32ms）认为卡顿
                Log.w("FPS", "Dropped frame: ${frameCost}ms")
            }
        }
        lastFrameTime = frameTimeNanos
        frameCount++
        Choreographer.getInstance().postFrameCallback(this) // 持续监听
    }

    fun start() {
        Choreographer.getInstance().postFrameCallback(this)
    }
}
```

### Q11：ANR 分析？

```
# ANR 日志位置
/data/anr/traces.txt（旧版本）
/data/anr/anr_*.txt（新版本）

# 典型 ANR 堆栈（主线程被锁阻塞）
"main" prio=5 tid=1 Blocked
  at com.example.MainActivity.onClick(MainActivity.java:42)
  - waiting to lock <0x12345678> (com.example.DatabaseHelper)
  - held by thread 18

"Thread-18" prio=5 tid=18 Timed_wait
  at com.example.DatabaseHelper.query(DatabaseHelper.java:88)
  - locked <0x12345678>

# 常见原因分类
# 1. 主线程网络 / 磁盘 IO 操作
# 2. 主线程等待锁（另一线程持有且耗时）
# 3. 死锁（两个线程互相等待对方的锁）
# 4. CPU 被其他进程抢占（系统繁忙，低端机常见）
# 5. 主线程 Binder 调用耗时（对端处理慢）
# 6. 主线程大量 View 操作 / 复杂布局
```

**ANR 预防：**

```kotlin
// 1. 严禁在主线程做耗时操作
// ❌
override fun onClick(v: View) {
    val data = okHttpClient.newCall(request).execute() // 主线程网络请求！
}

// ✅
override fun onClick(v: View) {
    lifecycleScope.launch(Dispatchers.IO) {
        val data = okHttpClient.newCall(request).execute()
        withContext(Dispatchers.Main) { updateUI(data) }
    }
}

// 2. 广播接收者中耗时操作放子线程
class MyReceiver : BroadcastReceiver() {
    override fun onReceive(context: Context, intent: Intent) {
        val pendingResult = goAsync() // 允许异步处理
        Thread {
            try {
                doHeavyWork()
            } finally {
                pendingResult.finish() // 必须调用，否则 ANR
            }
        }.start()
    }
}
```

## 六、网络性能优化

### Q14：网络请求优化？

**1. 接口缓存**

```kotlin
val client = OkHttpClient.Builder()
    .cache(Cache(File(cacheDir, "http"), 10L * 1024 * 1024))
    .addInterceptor { chain ->
        val request = if (isNetworkAvailable()) {
            // 有网：优先走网络，允许使用最多 60 秒的缓存
            chain.request().newBuilder()
                .header("Cache-Control", "public, max-age=60")
                .build()
        } else {
            // 无网：使用最多 7 天的缓存
            chain.request().newBuilder()
                .header("Cache-Control", "public, only-if-cached, max-stale=${7 * 24 * 3600}")
                .build()
        }
        chain.proceed(request)
    }
    .build()
```

**3. 数据压缩**

```kotlin
// 开启 Gzip 压缩（BridgeInterceptor 自动添加 Accept-Encoding: gzip）
// 服务端支持 Gzip 时自动压缩响应体，减少传输数据量

// 请求体压缩（上传大量数据时）
class GzipRequestInterceptor : Interceptor {
    override fun intercept(chain: Interceptor.Chain): Response {
        val originalRequest = chain.request()
        if (originalRequest.body == null) return chain.proceed(originalRequest)
        val compressedRequest = originalRequest.newBuilder()
            .header("Content-Encoding", "gzip")
            .method(originalRequest.method, gzip(originalRequest.body!!))
            .build()
        return chain.proceed(compressedRequest)
    }

    private fun gzip(body: RequestBody) = object : RequestBody() {
        override fun contentType() = body.contentType()
        override fun writeTo(sink: BufferedSink) {
            val gzipSink = GzipSink(sink).buffer()
            body.writeTo(gzipSink)
            gzipSink.close()
        }
    }
}
```
