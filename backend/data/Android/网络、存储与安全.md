## 一、HTTP 协议

### Q1：HTTP 各版本对比？

| 版本 | 特性 |
|------|------|
| HTTP/1.0 | 短连接，每次请求新建 TCP 连接 |
| HTTP/1.1 | 长连接（keep-alive），管道化（有队头阻塞问题） |
| HTTP/2.0 | 多路复用，头部压缩（HPACK），服务端推送，二进制分帧 |
| HTTP/3.0 | 基于 QUIC（UDP），解决 TCP 队头阻塞，0-RTT 握手 |

### Q2：HTTPS TLS 握手过程？

**TLS 1.2（2-RTT）：**

```
1. Client Hello：客户端支持的加密套件列表、随机数C
2. Server Hello：服务端选定套件、随机数S、下发证书
3. Client：验证证书合法性 → 生成预主密钥(Pre-Master Secret)
         → 用服务端公钥 RSA 加密后发送
4. 双方：用 C + S + Pre-Master 各自生成相同的会话密钥（对称密钥）
5. 后续：使用对称密钥加密通信
```

**TLS 1.3（1-RTT）：**
- 移除 RSA 密钥交换，只保留 ECDHE（前向安全）
- 支持 0-RTT 会话恢复（重连时无需完整握手）
- 握手延迟更低，安全性更高

---

### Q3：TCP 三次握手 / 四次挥手？

**三次握手：**

```
Client → SYN(seq=x)                  → Server
Client ← SYN+ACK(seq=y, ack=x+1)    ← Server
Client → ACK(ack=y+1)                → Server
```

**为何三次：** 防止历史重复连接被接受；确认双方收发能力均正常

**四次挥手：**

```
Client → FIN → Server    （客户端不再发送数据）
Client ← ACK ← Server   （服务端确认）
Client ← FIN ← Server   （服务端数据发完后，主动关闭）
Client → ACK → Server   （客户端确认）
Client 等待 2MSL 后进入 CLOSED
```

**TIME_WAIT 等待 2MSL 原因：**
- 确保最后一个 ACK 能到达对端（对端可能重传 FIN）
- 让旧连接的报文在网络中消失，防止被新连接误接收

## 二、OkHttp

### Q5：OkHttp 拦截器链？

```
application 拦截器（用户自定义）
    → RetryAndFollowUpInterceptor    // 失败重试、重定向处理
        → BridgeInterceptor          // 补全请求头（Content-Type/Cookie/gzip等）
            → CacheInterceptor       // 缓存读写（Cache-Control 策略）
                → ConnectInterceptor // 建立连接（复用连接池）
                    → network 拦截器（用户自定义）
                        → CallServerInterceptor // 实际向服务器发送请求
```

**addInterceptor vs addNetworkInterceptor：**

| 对比 | addInterceptor | addNetworkInterceptor |
|------|---------------|----------------------|
| 层级 | 应用层 | 网络层 |
| 缓存命中时 | 仍会执行 | 不执行 |
| 重定向 | 只执行一次 | 每次重定向都执行 |
| 适合场景 | 日志、统一参数 | 流量监控、原始请求 |

```kotlin
val client = OkHttpClient.Builder()
    .addInterceptor { chain ->
        // 添加公共请求头
        val request = chain.request().newBuilder()
            .addHeader("Authorization", "Bearer $token")
            .build()
        chain.proceed(request)
    }
    .addInterceptor(HttpLoggingInterceptor().apply {
        level = HttpLoggingInterceptor.Level.BODY
    })
    .build()
```

### Q6：OkHttp 连接池复用？

### Q8：Retrofit 动态代理原理？

```kotlin

fun <T> create(service: Class<T>): T {
    return Proxy.newProxyInstance(
        service.classLoader,
        arrayOf(service)
    ) { _, method, args ->
        // 触发 InvocationHandler.invoke()
        // 1. 解析方法注解（@GET、@POST、@Path、@Query 等）
        // 2. 构建 okhttp3.Request

        //    suspend 函数 → CoroutineCallAdapter
        //    Call<T> → DefaultCallAdapter
        // 4. 使用 Converter（GsonConverterFactory）序列化/反序列化
        loadServiceMethod(method).invoke(args)
    } as T
}
```

## 四、SharedPreferences vs MMKV

### Q11：SharedPreferences 缺点？

1. **多进程不安全**（`MODE_MULTI_PROCESS` 已废弃，数据可能丢失）
2. **全量写入：** 任何修改都重写整个 XML 文件，性能差
3. **主线程 I/O：** 首次 getSharedPreferences 解析 XML，可能阻塞主线程
4. **apply() 可能 ANR：** Activity onStop / onPause 时等待所有 apply 写完
5. **类型不安全：** 所有 value 存储为 Object，运行时才发现类型错误
6. **不支持加密**

---

### Q12：MMKV 原理？

**核心技术：mmap（内存映射文件）**

```
文件 ←── mmap ──→ 内存（直接映射到进程地址空间）
              ↓
       直接操作内存（OS 负责异步刷盘）
```

**优点：**
- 写入即内存操作，OS 异步刷盘（进程 Crash 也不丢数据，因为 mmap 由 OS 管理）
- 使用 protobuf 编码（比 XML 更紧凑高效）
- 支持多进程访问（文件锁机制）
- 增量追加写入（Append-only），性能极高
- 文件重整：空间不够时才触发全量写入

```kotlin
// 初始化
MMKV.initialize(context)

// 默认实例
val kv = MMKV.defaultMMKV()

// 多进程实例
val multiProcessKV = MMKV.mmkvWithID("multi", MMKV.MULTI_PROCESS_MODE)

// 使用
kv.encode("key_bool", true)
kv.encode("key_string", "hello")
kv.encode("key_int", 42)

val str = kv.decodeString("key_string", "defaultValue")
val num = kv.decodeInt("key_int", 0)

// 删除
kv.removeValueForKey("key_string")
```

## 五、SQLite & Room

### Q13：SQLite 优化？

**索引优化：**

```sql
-- 单列索引
CREATE INDEX idx_user_name ON users(name);

-- 联合索引（遵循最左前缀原则）
CREATE INDEX idx_user_name_age ON users(name, age);

-- 唯一索引
CREATE UNIQUE INDEX idx_user_email ON users(email);

-- 查看执行计划（是否用到索引）
EXPLAIN QUERY PLAN SELECT * FROM users WHERE name = 'Tom';
-- 输出：SEARCH TABLE users USING INDEX idx_user_name
```

**事务优化（批量操作必须用事务）：**

```kotlin
// Room 中使用 @Transaction
@Dao
interface UserDao {
    @Transaction
    suspend fun replaceAll(users: List<User>) {
        deleteAll()
        insertAll(users)
    }

    @Insert
    suspend fun insertAll(users: List<User>)

    @Query("DELETE FROM users")
    suspend fun deleteAll()
}

// 不用事务 vs 用事务（插入 1000 条）
// 不用事务：~3000ms（每条自动提交一次事务）
// 用事务：  ~30ms（批量提交）
```

**其他优化：**
- 使用 WAL 模式（Write-Ahead Logging）提升并发读性能
- 查询只取需要的列，避免 `SELECT *`
- 对频繁查询的条件字段建立索引

### Q14：Room 与 SQLite 的关系？

- Room 是 SQLite 的上层封装，底层仍是 SQLite
- 编译时检查 SQL 语句合法性（避免运行时崩溃）
- 自动处理 SQLite 线程切换（配合协程/Flow）
- 提供数据库迁移（Migration）支持
- 支持响应式查询（返回 Flow/LiveData，数据变化自动通知）

## 六、DataStore

### Q15：DataStore vs SharedPreferences？

| 对比 | SharedPreferences | DataStore |
|------|------------------|-----------|
| 线程安全 | 不完全安全 | ✅ 基于协程 |
| 主线程操作 | 可能阻塞 | ✅ 异步，不阻塞 |
| 错误处理 | 无 | ✅ Flow 异常处理 |
| 数据一致性 | 不保证 | ✅ 事务性写入 |
| 类型安全 | ❌ | ✅ Proto DataStore |
| 多进程 | 不安全 | ❌ 不支持（用 MMKV） |

```kotlin
// 定义 DataStore
val Context.dataStore by preferencesDataStore(name = "settings")

// 定义 Key
val KEY_USERNAME  = stringPreferencesKey("username")
val KEY_DARK_MODE = booleanPreferencesKey("dark_mode")
val KEY_FONT_SIZE = intPreferencesKey("font_size")

// 写入（挂起函数，在 IO 线程执行）
suspend fun saveSettings(username: String, darkMode: Boolean) {
    context.dataStore.edit { prefs ->
        prefs[KEY_USERNAME]  = username
        prefs[KEY_DARK_MODE] = darkMode
    }
}

// 读取（Flow，响应式，数据变化自动推送）
val username: Flow<String> = context.dataStore.data
    .catch { exception ->
        if (exception is IOException) emit(emptyPreferences())
        else throw exception
    }
    .map { prefs -> prefs[KEY_USERNAME] ?: "" }

// 在 ViewModel 中收集
val username = dataStore.data
    .map { it[KEY_USERNAME] ?: "" }
    .stateIn(viewModelScope, SharingStarted.WhileSubscribed(), "")
```

## 八、HTTPS 安全

### Q17：中间人攻击与防护？

**中间人攻击原理：**

```
正常：Client ←加密通信→ Server
攻击：Client ←→ 攻击者（伪造证书）←→ Server
攻击者可解密、篡改、重放所有通信内容
```

**防护方案 1：证书固定（Certificate Pinning）**

```kotlin
// OkHttp 证书固定（锁定服务器公钥 Hash）
// 获取公钥 Hash：openssl s_client -connect api.example.com:443 | openssl x509 -pubkey -noout | openssl pkey -pubin -outform der | openssl dgst -sha256 -binary | base64
val client = OkHttpClient.Builder()
    .certificatePinner(
        CertificatePinner.Builder()
            .add("api.example.com", "sha256/AAAA...Base64Hash...==")
            .add("api.example.com", "sha256/BBBB...BackupHash...==") // 备用证书
            .build()
    )
    .build()
```

**防护方案 2：双向认证（Mutual TLS）**

```kotlin
// 加载客户端证书
val keyStore = KeyStore.getInstance("PKCS12")
keyStore.load(assets.open("client.p12"), "password".toCharArray())

val kmf = KeyManagerFactory.getInstance(KeyManagerFactory.getDefaultAlgorithm())
kmf.init(keyStore, "password".toCharArray())

// 加载服务端信任的 CA
val trustStore = KeyStore.getInstance("BKS")
trustStore.load(assets.open("server-ca.bks"), "password".toCharArray())

val tmf = TrustManagerFactory.getInstance(TrustManagerFactory.getDefaultAlgorithm())
tmf.init(trustStore)

val sslContext = SSLContext.getInstance("TLS")
sslContext.init(kmf.keyManagers, tmf.trustManagers, null)

val client = OkHttpClient.Builder()
    .sslSocketFactory(sslContext.socketFactory, tmf.trustManagers[0] as X509TrustManager)
    .build()
```

## 十、数据加密

### Q19：AES vs RSA 使用场景？

| 算法 | 类型 | 密钥长度 | 优点 | 缺点 | 场景 |
|------|------|---------|------|------|------|
| AES | 对称加密 | 128/256 bit | 速度快，适合大量数据 | 密钥分发困难 | 本地数据加密、传输大量数据 |
| RSA | 非对称加密 | 2048/4096 bit | 密钥可安全分发 | 速度慢，不适合大量数据 | 加密 AES 密钥、数字签名 |

**实践（混合加密）：**

```
1. 客户端生成随机 AES 密钥（256 bit）
2. 用服务器 RSA 公钥加密 AES 密钥
3. 用 AES 密钥（GCM 模式）加密实际业务数据
4. 发送：RSA 加密的 AES 密钥 + AES 加密的数据 + IV
5. 服务端用 RSA 私钥解密 AES 密钥，再解密数据
```

```kotlin
// AES-GCM 加密（推荐，带完整性验证）
fun aesEncrypt(data: ByteArray, key: ByteArray): Pair<ByteArray, ByteArray> {
    val cipher = Cipher.getInstance("AES/GCM/NoPadding")
    val keySpec = SecretKeySpec(key, "AES")
    cipher.init(Cipher.ENCRYPT_MODE, keySpec)
    val iv = cipher.iv          // 12 字节随机 IV
    val encrypted = cipher.doFinal(data)
    return Pair(iv, encrypted)
}

fun aesDecrypt(encrypted: ByteArray, key: ByteArray, iv: ByteArray): ByteArray {
    val cipher = Cipher.getInstance("AES/GCM/NoPadding")
    val keySpec = SecretKeySpec(key, "AES")
    val gcmSpec = GCMParameterSpec(128, iv)
    cipher.init(Cipher.DECRYPT_MODE, keySpec, gcmSpec)
    return cipher.doFinal(encrypted)
}

// RSA 加密 AES 密钥
fun rsaEncrypt(data: ByteArray, publicKey: PublicKey): ByteArray {
    val cipher = Cipher.getInstance("RSA/ECB/OAEPWithSHA-256AndMGF1Padding")
    cipher.init(Cipher.ENCRYPT_MODE, publicKey)
    return cipher.doFinal(data)
}
```

```kotlin
// 使用 Android Keystore 存储密钥（密钥不可导出，硬件级保护）
```
